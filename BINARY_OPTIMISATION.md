# GhostESP binary optimisation audit

This audit records the development checkout. The source-only copy omits the
historical `build/backups/`, `build/releases/`, `build/binary-audit/` and `dist/`
artifacts cited below; a new `bash build.sh` creates its own build and package.

Audit and implemented follow-up for the ESP32-2424S012, 15 November 2026.
The first sections preserve the original measurements. The implemented release
and screensaver results follow below; storage/RAM savings are distinct from
unmeasured menu-latency improvements.

Baseline app (archived in `build/backups/optimization-baseline/`): **3,295,120 bytes**,
SHA-256 `a564da7ef879d40c252f826df87f7219856b1c7e6aad77ab88f6d9a986236515`.
Source, IDF and dependency revisions remain those recorded by this port.

## What is in the flashed image

| Section | Bytes | Meaning |
|---|---:|---|
| Flash code | 2,115,482 | Instructions normally executed through the flash cache |
| Flash data | 1,031,280 | Constants, strings, assets, initializers and app descriptor |
| IRAM code | 125,068 | Instructions loaded into internal RAM |
| Initialized DRAM | 23,129 | Initial values stored in the image and copied to RAM |
| DRAM BSS | 72,336 | RAM reservation; zero-filled at startup, not stored as a full byte array in the image |

These figures are not independent pools to add together as available memory.
Code, data, image headers and alignment account for the app file. The C3 shares
internal memory between instruction/data uses. Linker free-space figures do not
include all runtime tasks, drivers or heap allocations. Earlier runtime tests
recorded a minimum of only **628 bytes** of free internal RAM, so memory headroom
is a higher priority than shaving a few instructions from a cold function.

Already enabled: `-Os`, per-function/per-data sections, linker `--gc-sections`,
160 MHz CPU, 80 MHz flash, and RISC-V compressed instructions. Exceptions and RTTI
are disabled. The minimum supported chip revision is already C3 v0.3, so the
usual recommendation to raise it to v0.3 has already been applied.

## Stripping: measured zero flash saving

On copies under `build/binary-audit/`, GNU `strip --strip-all` changed:

| Artifact | Before | After |
|---|---:|---:|
| ELF file on the development computer | 29,918,964 bytes | 5,596,764 bytes |
| Application regenerated by esptool | 3,295,120 bytes | 3,295,120 bytes |

The executable segments were identical. Differences in the regenerated images
were confined to the ELF identity hash at file offsets 176–207 and the image
checksum/SHA-256 footer. Normalizing that metadata made the images identical.
The `.debug_*` sections were never part of the flashed image. A raw `.bin` has
no ELF symbol table for `strip` to remove.

Keep the unstripped ELF and map for each released image. They cost no device
storage and allow addresses in that exact optimized build to be decoded; source
alone does not preserve that address mapping. Compressing a download/backup
also does not reduce installed application size. Esptool already compresses the
serial transfer, then writes the full image to flash.

## Priorities

| Priority | Change to investigate | Evidence and trade-off |
|---|---|---|
| 1: runtime RAM | Compile out the unused wired-peer communication implementation, retaining unsupported/no-op APIs | `esp_comm_manager.c.obj` still retains 6,268 bytes of static DRAM and 10,178 bytes of flash code/data. Its startup is disabled on this board, but CLI/API references keep the implementation linked. These are candidate upper bounds, not measured savings after a replacement. |
| 2: flash and logging overhead | Reduce compiled log maximum; use silent assertions/error checks | Runtime default is WARN but compiled maximum is VERBOSE. Lowering runtime verbosity alone cannot remove those instructions/strings. Keep allocation checks: silent checks reduce messages without deliberately continuing through failures. |
| 3: responsiveness | Measure and reduce full-screen redraws, synchronous radio work on the UI path, and SPI transaction overhead | The display uses a single five-line buffer at a configured 20 MHz. A full square RGB565 frame is 115,200 bytes: 46.08 ms of pixel wire time before commands, rendering and task scheduling. Assembly cannot remove that transfer time. |
| 4: flash assets | Consolidate retained fonts and optional artwork; review optional lookup/certificate data | Seven retained Montserrat sizes total 105,747 bytes; the OUI table is 64,537 bytes, the X.509 bundle 66,984 bytes, eleven 50×50 maps 82,500 bytes and the logo map 28,650 bytes. Removal changes presentation or feature coverage. |
| 5: runtime RAM | Reduce SPI queue depth and task stacks after measurement | SPI reserves sixteen transaction descriptors plus queues despite the single draw buffer and frequent transaction drains. Test a smaller pool. Serial uses an 8,192-byte stack and previously reported 4,564 bytes unused, but that workload is not proof that every command fits a smaller stack. |
| 6: CPU hot paths | Compare selected files at `-O2`; retain `-Os` elsewhere | The measured blend-file experiment below substantially increases IRAM. A whole-project switch needs a complete linked size comparison and device timing. |

The wired-peer change must also reject direct initialization on this board;
generic UART defaults use GPIO6/7, which belong to the LCD. Removing only its
startup call leaves both the linked memory and reachable initialization code.

The linker reports 436,893 bytes under
`.rodata.esp_stdio_register.str1.4`, although that input section was originally
only 93 bytes. This is a merged string pool, not a 437 KB console implementation.
Do not remove console support based on that archive attribution. A simple scan
found 58,248 bytes of INFO/DEBUG/VERBOSE-prefixed format strings in this pool.
That is a candidate set, not a prediction of final image savings: merging,
module-local log levels and prebuilt libraries affect what can disappear.
User-facing `glog`/terminal results are a separate path and should remain
available for the WebUI log-saving workflow.

The WebUI is already gzip compressed to 52,309 bytes. Montserrat 40 is configured
but absent from the retained font objects; disabling that setting alone would
not recover its nominal font size. Only retained sections consume flash.

## Assembly findings and compiler experiment

Disassembled the actual linked `lv_color_fill`, `lv_draw_sw_blend_basic`,
`round_list_fit_event`, `GC9A01_flush` and `disp_spi_transaction` functions.

- `lv_color_fill` is already in IRAM and just 76 bytes. Its main loop performs
  eight aligned 32-bit stores per iteration, filling sixteen RGB565 pixels.
  A handwritten assembly replacement has little obvious room for improvement.
- Round-list fitting already uses integer geometry. The disassembly includes a
  signed divide for the centre calculation and calls the integer width helper.
  A small lookup table or cached widths could reduce repeated geometry work,
  but should follow a profile showing that this work is material. LVGL layout
  passes and invalidations may cost more than the arithmetic.
- The GC9A01 flush path waits for pending transactions around commands/data.
  With a five-line buffer, a square full refresh requires at least 48 color
  chunks. Reducing synchronization/command overhead or improving dirty regions
  is a stronger candidate than manually shortening its coordinate arithmetic.

Recompiled only `lv_draw_sw_blend.c` using its exact recorded compiler command,
changing `-Os` to `-O2` and writing a separate object:

| Retained input section sizes in that object | `-Os` | `-O2` |
|---|---:|---:|
| Code plus read-only data | 3,550 bytes | 6,548 bytes |
| Main IRAM blend section (`.iram1.6`) | 2,860 bytes | 5,688 bytes |

This is an object comparison, not a final link or speed benchmark. Larger code
may execute faster, but additional IRAM use competes with the RAM needed for
stable UI/radio operation. C3 has no Xtensa SIMD instructions; implementations
written for other ESP32 families cannot simply be copied into this RISC-V port.

LTO is an experimental option here, not an available switch to assume works:
the pinned IDF explicitly adds `-fno-lto`, and no matching compiler LTO Kconfig
option was found. Newer IDF documentation describes support not present in this
checkout. Retrofitting LTO or upgrading IDF requires a separate compatibility
test with linker section placement, prebuilt radio libraries and retained APIs.

## Measurement needed before changing the release

Use a repeatable workload: menu scroll, all keyboard pages, return from BadBLE,
terminal output and WebUI log retrieval. Record touch-release-to-visible-update
latency (median and 95th percentile), render/flush durations, dropped input,
minimum/largest free heap and task stack high-water marks. The binary and
disassembly identify candidates; they do not establish which function consumes
the most time during that workload.

First implement board-specific removal of unused peer code and a lean logging
profile. Compare whole-image bytes and runtime RAM with the baseline. Next
instrument redraw/flush timing and move lengthy radio transitions out of the UI
callback where measurements show blocking. Only then evaluate selective `-O2`,
a geometry lookup table or an assembly kernel. Test LCD clock increases and QIO
flash separately after confirming hardware support; they are not safe generic
settings. Larger/double draw buffers must wait for adequate RAM headroom.

Retained audit outputs are local under `build/binary-audit/`: section/component/file
sizes, disassembly samples, compiler-experiment measurements and
`strip-results.json`. Temporary stripped ELF/image copies and compiler objects
were removed after measurement. These are analysis artifacts, not flash images
to deploy. The original image, ELF, map and sdkconfig are retained locally under
`build/backups/optimization-baseline/`; `dist/` now contains the optimized build.

To inspect sizes again using the pinned tools:

```sh
bash build.sh size
bash build.sh size-components
bash build.sh size-files
```

Primary references: [ESP-IDF v6.1 binary size guide](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32c3/api-guides/performance/size.html)

## First optimized release: lean checks, no wired peer, bounded SPI, Neon saver

Applied the first two priorities and the SPI-pool reduction, retaining `-Os`:

- On this board every wired-peer API is an allocation-free unsupported/no-op
  stub. Direct initialization cannot claim LCD GPIO6/7. The original implementation
  remains available to other boards. No peer UART buffers, queues or task can be
  created here; the stub object has zero static writable data.
- Compiled log maximum is INFO (3), runtime default remains WARN (2).
  DEBUG/VERBOSE log sites disappear where the IDF macros permit it. INFO remains
  available for explicit `mem heaps` diagnostics. `glog`, WebUI log saving and
  command results remain. Per-module overrides/prebuilt libraries can retain
  some higher-level messages.
- Assertions and ESP error checks use the silent profile. They still stop on a
  failure, with fewer retained diagnostic strings; they are not compiled away.
  LVGL allocation checks remain. Obsolete preset assertion aliases are removed
  before config migration so the profile really resolves to level 1.
- Board-specific SPI transaction pool/driver queue depth is four instead of
  sixteen. One five-line draw buffer and the GC9A01's transaction drains remain.
  Other display boards retain sixteen.
- Added Neon Vortex, documented in [SCREENSAVER.md](SCREENSAVER.md). It uses
  flash lookup tables, integer rotozoom, incremental radial math, palette
  cycling and globally aligned 2×2 sampling. It writes straight into the existing
  buffer and sleeps when hidden. No full-frame image, libm kernel or extra task.
- Disassembly of the first raster exposed four signed constant divisions,
  including halving each pixel's signed wave sum: `-Os` chose compact DIV
  instructions. Explicit shift/rounding-correction expressions remove all four
  DIV instructions while preserving truncation toward zero. Six golden-frame
  hashes from the original kernel, partial-strip tests and sanitizers match.
  The revised raster is 568 code bytes versus 532, a 36-byte size trade-off.
  This is source-level instruction tuning verified in the actual RISC-V ELF;
  no handwritten assembly or binary patch is needed.

| Whole-release measure | Original | Optimized, including saver | Reduction |
|---|---:|---:|---:|
| App binary bytes | 3,295,120 | 3,082,240 | 212,880 (6.46%) |
| Flash code (`.flash.text`) | 2,115,482 | 2,032,980 | 82,502 |
| Flash constants (`.flash.rodata`) | 1,030,756 | 917,000 | 113,756 |
| IRAM code (`.iram0.text`) | 125,068 | 113,386 | 11,682 |
| Initialized DRAM (`.dram0.data`) | 23,129 | 18,197 | 4,932 |
| Zero-initialized DRAM (`.dram0.bss`) | 72,336 | 65,736 | 6,600 |
| Sum of those three internal-RAM sections | 220,533 | 197,319 | 23,214 |

These are combined release deltas, not isolated savings attributed to each
switch. Padding and driver/runtime allocations are outside the three-section
RAM sum. Smaller IRAM code can free internal memory for data; it does not imply
those instructions got faster. Freed flash is **980,992 bytes** inside the
existing app partition, not a newly mounted storage filesystem.

Optimized app SHA-256:
`d813ae53f605463dc64c997eb4e568b46de30e0e9dcfcf65b55f8751cd239bae`.
The exact ELF/map for this release are archived in
`build/releases/d813ae53f605/`; keep them with this image for crash decoding. The raw comparison is in
`build/binary-audit/implemented-results.json`.

Stripping remains a zero-device-saving operation, so no post-link `.bin`
editing was applied. No handwritten assembly, project-wide `-O2`, unsupported
LTO switch, flash mode change or LCD overclock is part of this release. Font,
certificate and artwork removal remain feature/presentation trade-offs.

### Device checks

The application was flashed at 0x10000 on `/dev/tty.usbmodem101`; esptool verified
the written hash. Existing settings and partition layout were preserved. It
booted and responded to `identify`, the raster benchmark and heap diagnostics.
After `saver bench`, the final image reported **47,944 bytes free** internal
8-bit heap, largest block **38,912**, minimum **45,312**; `mem check` returned
`heap integrity: ok`. This is a point-in-time observation, not an apples-to-apples
comparison with the earlier WebUI/BLE workload. Runtime logging was restored to
WARN after diagnostics.

The 32-frame `saver bench` took 224,936 microseconds total: **7,029 microseconds
per raster frame**, including explicit yields and task scheduling, excluding SPI.
An unlocked active-saver sample without mirroring counted 32 frames in 4,127 ms:
**7.7 fps**, raster average **7,385 microseconds**, maximum **7,656 microseconds**.
This short sample is not a sustained rate guarantee. It shows that drawing math
is much faster than the observed complete refresh cycle; transfer/flush waits,
LVGL and scheduling need attention before more arithmetic tuning. The nominal
20 fps request ceiling was not reached on the present five-line driver.

A locked screen correctly rejected saver activation, and a later screenshot
showed the slide-to-unlock screen after idle locking. The captured screenshots
are local under `build/saver-device-0.png` and `build/saver-final-0.png`; they are
not proof of motion or a physical touch/return-to-menu acceptance test.

All four native CTest targets pass, including actual LVGL strip pixels and 100
saver lifecycle cycles. The existing touch-frame and exhaustive circular-layout
checks pass, resolved build flags are asserted, and the saved patch reproduces
all 35 modified/new upstream files. Raster ASan/UBSan checks pass.

A general responsiveness gain has not been quantified. To assess that, repeat
the menu/keyboard/BadBLE/WebUI workload from the measurement section with a fixed
radio state and input sequence. Do not equate higher free heap with a measured
lower median or 95th-percentile touch latency.


## Copper Dream / DMA / Orbital Vector follow-up

The combined release adds the Future Crew-inspired procedural scene, local
compiler/IRAM tuning, two-buffer SPI DMA with yielding completion waits, and
an original Gyruss-inspired vector-style orbital shooter. See
[RISC_V_OPTIMISATION.md](RISC_V_OPTIMISATION.md) for the measured C/ASM comparison,
[SCREENSAVER.md](SCREENSAVER.md) for effects/commands, and
[ORBITAL_VECTOR.md](ORBITAL_VECTOR.md) for game controls and math.

| Whole-release measure | Before this follow-up | Combined release |
|---|---:|---:|
| App binary | 3,082,240 | 3,090,976 |
| Flash code | 2,032,980 | 2,040,402 |
| Flash constants | 917,000 | 918,064 |
| IRAM code | 113,386 | 113,608 |
| Initialized DRAM | 18,197 | 18,229 |
| BSS | 65,736 | 65,952 |
| Those three internal-RAM sections | 197,319 | 197,789 |

The new features/diagnostics add 8,736 image bytes and 470 bytes across those
internal-RAM sections. Runtime draw-buffer storage increases by 2,400 bytes,
plus a small completion-semaphore allocation. Those heap allocations are not
included in the section sum. Relative to the original 3,295,120-byte build,
the combined application remains **204,144 bytes smaller** and those RAM sections
remain **22,744 bytes smaller**. This is not a claim of 22,744 additional free
runtime heap after all new allocations.

The app partition has **972,256 bytes** free. Application SHA-256:
`5f13ade9821b9cb1d0c5428175cad46d2b47a3cf61cd301c0002e0b3534ed9fc`.
All 44 upstream modified/new files are captured by the reproducible patch.
`ROUND_CREW_PROFILE=0` removes development-only scene comparison copies.

Eight native CTest cases pass, including delayed ping-pong completion, both
procedural rasters and Orbital Vector model/UI lifecycle. The model checks
150,000 deterministic steps. Pure model/raster sanitizer tests pass. These tests
establish buffer/math/lifecycle properties; physical touch feel, sustained LCD
rate and long Wi-Fi/BLE soak remain separate device acceptance checks.

### Device observations for the combined release

The application was flashed at `0x10000`, with esptool verifying its hash; NVS
and the partition layout were preserved. All five palette kernels returned
matching pixels for every packed byte and unaligned destination offsets 1–3.
Best times remained 269/232/232/220/304 microseconds per 32 scanlines for
C-Os/C-O2/C-O3/C-O3-IRAM/ASM-IRAM respectively.

A short Copper Dream sample counted 19 frames in 2,145 ms: **8.8 fps**, raster
average **6,789 microseconds**, maximum **7,270 microseconds**. This followed
radio/navigation activity and is not a controlled comparison with the earlier
Neon Vortex sample. The measured complete refresh rate is below the 20 fps
request ceiling. Math tuning alone has not eliminated display/scheduling costs.

After radio activity and navigation, `mem heaps` reported 31,968 free internal
8-bit bytes, largest block 15,872 bytes and minimum free 17,684 bytes.
`mem check` reported heap integrity OK. These figures are a workload snapshot,
not a minimum guaranteed allocation budget. Runtime logging was restored to WARN.

Orbital Vector was opened on the device and both its opening panel and active
gameplay were captured through the USB mirror. The final UI hides/restores the shared status bar and explicitly
sets the pause panel text contrast. Screenshot capture perturbs timing; no
sustained gameplay frame rate or physical touch latency is claimed.
